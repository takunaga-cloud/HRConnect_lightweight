# HRConnect 運用仕様書

## 1. 監視・アラート設計 (Monitoring & Alerting)

本システムはAWSサーバーレス構成を採用しているため、OSやサーバー自体の監視は不要ですが、APIの稼働状況やアプリケーションエラー、リソース制限に焦点を当てて監視を行います。

### 1.1 ログ収集 (Log Collection)
* **Amazon CloudWatch Logs**: 
  * AWS Lambdaの実行ログ（FastAPIのコンソール出力、未キャッチ例外スタックトレース）、API Gatewayのアクセスログを自動収集します。
  * ログ保存期間: **90日間**（開発環境は14日間）。

### 1.2 アラート通知の閾値と重要度 (Alert Thresholds & Severity)

| 監視対象項目 | 監視方法 / ログソース | 閾値・検知条件 | アクション (連絡先) |
| :--- | :--- | :--- | :--- |
| **システム例外 (Severe Error)** | CloudWatch Metric Filters | FastAPIログ内で `[ERROR]` または `[CRITICAL]` が **5分間に3回以上** 発生 | システム開発運用チームへ即時Slack & Eメール通知 |
| **APIエラー率 (API Error Rate)** | API Gateway Metrics | HTTP `5XX` エラー率が **5分間で 2%** を超過 | 運用チームへ即時通知 |
| **データベース負荷 (DB Load)** | DynamoDB Metrics | 読み込み/書き込みキャパシティユニット (RCU/WCU) のスロットリング発生率が **5分間に1%以上** | データベース管理者へ警告通知 |
| **監査ログ不整合 (Audit Failure)** | S3 Access Logs / KMS | 監査ログバケットに対する書き込み失敗、または削除ポリシー違反の検知 | セキュリティ責任者へ即時緊急通知 |

## 2. 監査ログ要件と運用 (Audit Logs Management)

労務管理システムとしてコンプライアンス（改ざん防止・証跡確保）を満たすため、すべての主要な変更操作は監査ログとして記録され、セキュリティ部門によってのみ読み取り可能な状態で保管されます。

### 2.1 監査ログの対象イベント
* **認証イベント**: ログイン成功/失敗、パスワードリセット、MFA設定変更。
* **マスタデータ操作**: `users`, `work_rules`, `projects` などの作成・変更・削除。
* **申請・承認処理**: 各種申請の起票、承認、却下、差し戻し操作（操作者ID、タイムスタンプ、承認対象者IDを含む）。
* **実績・締め操作**: 月次締め処理の実行、ロック解除、および給与・工数データのCSV/Excelエクスポート操作。

### 2.2 監査ログのデータ構造（ログの一例）
監査ログはJSON形式で記録され、個人情報やパスワードなどの機密情報はマスキングされた状態で保存されます。

```json
{
  "timestamp": "2026-05-31T03:00:00.123Z",
  "event_id": "uuid",
  "user_id": "operator-user-uuid",
  "client_ip": "203.0.113.195",
  "event_type": "APPLICATION_APPROVED",
  "target_resource": "Application",
  "target_id": "target-application-uuid",
  "result": "SUCCESS",
  "details": {
    "applicant_id": "employee-user-uuid",
    "application_type": "PaidLeave",
    "approved_days": 1.0
  }
}
```

### 2.3 監査ログの保管仕様
* **保存場所**: Amazon S3 (セキュリティ専用バケット)。
* **改ざん防止**: S3 Object Lock機能（コンプライアンスモード）を使用し、いかなるユーザー（管理者権限含む）による削除・上書きも禁止します。
* **保存期間**: **最低7年間**（労働基準法等に関連する文書の保存義務に準拠）。S3ライフサイクルルールにより、作成から1年経過したログは Glacier Flexible Retrieval へ自動移行し保管コストを削減します。

## 3. バックアップ・リストア方針 (Backup & Restore)

データベース（Amazon DynamoDB）の障害や誤操作によるデータ消失に備え、以下のバックアップ体制を確立します。

### 3.1 自動バックアップ
* **ポイントインタイムリカバリ (PITR)**: DynamoDB の PITR 機能を有効化し、過去 35 日間の任意の時点にデータを秒単位で復元できるようにします。
* **オンデマンドバックアップ**: 月次締め完了時などの節目において、オンデマンドバックアップ（手動スナップショット）を作成し、アーカイブ保管します。

### 3.2 目標復旧時点 (RPO) と 目標復旧時間 (RTO)
* **目標復旧時点 (RPO)**: **最大5分**（PITRにより、障害発生直前の状態まで秒単位で復旧可能）。
* **目標復旧時間 (RTO)**: **1時間以内**（PITRからのテーブル復元、およびLambda環境変数のテーブル名切り替え手順を含む）。

## 4. システム制限事項 (System Limits)

安定的な運用を維持するため、本システムには以下の制限事項が設定されています。

* **日付表示および入力形式の統一制限**:
  * すべての画面上の日付表示、およびテキスト・カレンダーによる手動入力は **`YYYY/MM/DD`** 形式に制限されます。
  * ブラウザの言語設定やロケール（例: 米国英語設定での `MM/DD/YYYY`）に関わらず、本形式が強制されます。これに反する形式の入力や表示はフロントエンドのバリデーションによって却下されます。
* **打刻時の位置情報 (GPS) 精度制限**:
  * モバイル打刻の際、GPSの測定精度精度（`accuracy`）が **100メートルを超える** 場合は、不正な位置偽装を防ぐため警告メッセージを表示します。
* **申請時の添付ファイル制限**:
  * 領収書や証明書などの添付ファイルは、1ファイルあたり **最大10MB** とし、ファイル形式は `PDF`, `JPEG`, `PNG` のみに制限します。
* **大量データ出力制限**:
  * 1回のエクスポート処理で処理可能な勤怠・工数データは、パフォーマンス維持のため最大 **50,000件（または所属人数500人の1か月分）** までとし、これを超える場合は期間を分割して出力することを要求します。
