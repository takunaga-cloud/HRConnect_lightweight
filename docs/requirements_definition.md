# HRConnect 要件定義書

## 1. はじめに (Introduction)

### 1.1 システムの目的
本システム「HRConnect」は、「勤怠管理」「シフト管理」「ワークフロー（諸届申請）」、および「工数管理（日報）」を単一のプラットフォームで統合管理するオールインワン労務管理システムです。
複数の既存ツールをまたぐことによる転記作業や整合性の破綻を防ぎ、日本の複雑な就業規則や36協定に準拠したセキュアな業務基盤を提供します。

### 1.2 解決したいビジネス課題
1. **多重入力・転記ミスの削減**:
   有給休暇の申請・承認が、勤怠実績（有給残日数）やシフト予定に自動で連動しないため、管理部門が手作業で転記する手間とミスが発生している。
2. **プロジェクト収支の可視化**:
   「従業員がどのプロジェクトのどの作業に何時間使ったか」という工数実績と、実際の労働時間（勤怠データ）が乖離しており、プロジェクト別の正確な労務コストが把握できない。
3. **複雑な就業ルールの吸収**:
   フレックスタイム制、変形労働時間制、各種休憩ルール、打刻丸め処理、36協定（残業上限）など、企業や雇用形態ごとに異なる日本の複雑な就業ルールに対応しきれていない。
4. **セキュリティと可用性**:
   個人情報や労務情報などの機密データを扱うにあたり、セキュアな認証基盤と、打刻ラッシュ時（朝9時など）に耐えられる柔軟なインフラ性能が求められている。

## 2. ターゲットユーザー (Target Users)

### 2.1 一般従業員 (Employee)
* **利用シーン**: スマートフォンやPCから、日々の打刻、シフトの確認、日報としての工数入力、各種申請（休暇、残業、打刻修正など）を行う。
* **ニーズ**: モバイルから簡単に打刻ができ、自分の労働時間や有給残日数をいつでも確認できること。

### 2.2 管理者（PM・店長・部門長）(Manager / Leader)
* **利用シーン**: PCから、部下のシフト作成・調整、申請の承認・却下、部下の工数予実確認、36協定アラートのモニタリングを行う。
* **ニーズ**: 自分のチームの労働状況を一目で把握し、コンプライアンス違反（過剰残業など）を未然に防げること。

### 2.3 人事・労務・経理 (HR / Payroll)
* **利用シーン**: 全社の月次締め処理、給与計算ソフト（弥生給与、freeeなど）連携用データの出力、組織マスタや就業規則マスタの設定管理を行う。
* **ニーズ**: 締め処理がスムーズに行え、給与計算に必要なデータが正確かつ加工不要な状態で出力できること。

## 3. 機能要件 (Functional Requirements)

### 3.1 認証・認可要件 (Authentication & Authorization)
* **認証**: Amazon Cognitoを用いたセキュアなログイン認証。多要素認証 (MFA) のサポート。
* **権限モデル**: ロールに基づく認可制御 (RBAC) の適用。
  * `Admin`: 全管理機能へのアクセスおよびシステム設定。
  * `Manager`: 部下の管理（シフト、申請承認、アラート確認）。
  * `Leader`: 特定プロジェクトの管理とメンバーの工数確認。
  * `HR_Payroll`: 月次締め、給与データ出力、就業規則設定。
  * `Employee`: 自身の打刻、シフト確認、工数入力、申請。

### 3.2 勤怠管理要件 (Attendance Management)
* **打刻機能**:
  * PCおよびスマートフォン（レスポンシブ）による出勤、退勤、休憩開始、休憩戻り打刻。
  * 打刻時の位置情報 (GPS)、IPアドレス、デバイス情報の自動取得。
* **労働時間計算**:
  * 就業規則（`WorkRule`）に基づく打刻の丸め処理（例: 出勤は切り上げ、退勤は切り捨て）。
  * 実労働時間、所定労働時間、時間外労働（残業）、深夜労働時間の自動計算。
  * 休憩時間の自動控除機能（例: 6時間超で45分、8時間超で60分自動控除）。

### 3.3 シフト管理要件 (Shift Management)
* **予定管理**:
  * 日ごとの勤務予定（開始・終了時刻、休日設定）の登録。
  * 定型シフトパターン（早番、遅番など）のテンプレート登録と適用。
* **予定と実績の比較**:
  * シフト予定と実際の打刻データの突合による遅刻・早退・欠勤の自動判定。

### 3.4 工数管理要件 (Man-hour Management)
* **工数入力（日報）**:
  * 従業員が「どのプロジェクト（`Project`）のどのタスクカテゴリ（`TaskCategory`）に何分使用したか」を登録する。
* **勤怠連携バリデーション**:
  * 1日の工数入力値の合計が、その日の実際の労働時間（勤怠データの実働時間）と一致しているかを検証する。
  * 設定された許容誤差（例: ±15分）を超える場合は、警告表示または保存制限を行う。
* **プロジェクト予実管理**:
  * プロジェクトごとの予算工数と実績工数の可視化。

### 3.5 ワークフロー（諸届申請）要件 (Workflow & Applications)
* **各種申請**:
  * 有給休暇申請、残業申請、打刻修正申請など。
  * 申請フォームはテンプレート（JSON Schema）によって動的に定義・拡張可能であること。
* **申請と勤怠・シフトの自動連動（副作用処理）**:
  * **有給休暇承認時**: 有給休暇管理台帳（`PaidLeaveLedger`）から自動で日数を消化し、対象日のシフトを「有給」に自動変更する（半休の場合は所定の勤務時間を自動割当）。
  * **打刻修正承認時**: 対象日の勤怠実績（打刻データ）を自動で修正し、労働時間を再計算する。

### 3.6 締め処理・外部連携要件 (Closing & Data Export)
* **月次締め**:
  * 管理者による月次データのロック処理。ロック後は、対象月の勤怠・シフト・工数・申請の変更を不可とする。
* **データ出力**:
  * 給与計算ソフト連携用のCSV出力、工数集計用のExcel/CSV出力。
  * 大量データ出力時のメモリ枯渇対策（ストリーム処理など）。

## 4. 非機能要件 (Non-Functional Requirements)

### 4.1 セキュリティ (Security)
* **通信暗号化**: すべての通信はHTTPSで暗号化される。
* **データ暗号化**: Database (Amazon DynamoDB) および S3 バケットのデータは保管時に自動的に暗号化される。
* **監査ログ**: ユーザーのログイン、データの作成・更新・削除、承認操作、月次締めやエクスポートなどの全操作履歴を監査ログとして記録し、改ざん不可能な状態で長期保管（最低7年間）する。
* **不正アクセス防止**: APIはすべて有効なCognito JWTトークンによる認可を必須とし、不正アクセスを遮断する。

### 4.2 可用性・信頼性 (Availability & Reliability)
* **AWSサーバーレスの採用**: Lambda、DynamoDBなどを採用し、打刻ラッシュ時の自動スケーリングと、夜間や閑散期における完全なコスト最適化（10人規模等の小規模利用では無料枠に収まり基本料金ほぼゼロ）を両立する。
* **トランザクション制御**: 申請承認や工数一括保存などの複合的なデータ更新処理は、データベースのトランザクション内で実行し、データの部分的な反映による不整合を完全に防止する。

### 4.3 コンプライアンス・法規制対応 (Compliance)
* **36協定アラート**:
  * 日本の労働基準法に基づく残業時間上限チェック。
  * 月次の労働時間集計時に、`WorkRule`で設定された36協定の閾値（例: 月45時間）に近づいた場合、警告フラグを検出して管理者および従業員に通知する。

## 5. UI/UXにおける共通表示要件 (UI/UX Common Requirements)
* **日付形式標準化ルール**:
  * システム全体の画面および入力インターフェースにおいて **`YYYY/MM/DD`** 形式での統一を要件とします。
  * クライアント環境（OSやブラウザのロケール設定など）に起因する表記ブレ（`MM/DD/YYYY` などへの切り替わり）を防ぐため、標準の `<input type="date">` は使用せず、共通の `DateInput` コンポーネントを使用してください。
  * 本ルールは一切の変更を禁止します。
